# bookmarks

一个本地离线的 AO3 书签页替代品：把同人小说以个人书库的形式存在本地磁盘上，这样即使作品在上游被隐藏或删除，也依然找得回来。

状态：**可运行的桌面应用。** 导入、分组、去重、译文配对、搜索、筛选、排序、编辑都已端到端可用。剩余工作列在文末。

[English](README.md) | **中文**

## 运行

```
npm install
npm run app:dev          # 开发服务器 + 带热重载的窗口
npm run app:build        # Windows .exe + 安装包（NSIS、MSI）
```

设置存放在 `%APPDATA%\com.bookmarks.app\settings.json`，只有几百字节，记录书库位置、主题、字号和分组方式。这个路径由 identifier 决定，所以改动它会让已有的配置"消失"。

书库本体——`bookmarks.db` 加 `library/`——刻意不放在 `%APPDATA%` 里，这样 C 盘快满也不会让书库无法工作。位置在设置面板里指定；从未选过时的默认值是 `%USERPROFILE%\Documents\bookmarks`，而 `BOOKMARKS_LIBRARY` 可以覆盖以上两者，这让测试和临时运行不会碰到真实书库。状态栏显示实际解析出的路径，工具栏则有按钮直接打开该文件夹，方便备份。

默认值是从用户目录推导出来的，而不是写死的，所以别人克隆之后，绝不会在一个"只存在于原作者机器上"的盘符里创建书库。`Documents` 通常位于 C 盘，而这恰恰是这个设置项想规避的情况——所以如果书库变大了，把它指到空间更宽裕的地方。

## 目录结构

```

  src/store.rs                     书库本体：按编号的作品目录、文件副本
  src/view.rs                      界面消费的读取模型
  src/text.rs                      折叠 / 搜索匹配 / 字数统计
  src/date.rs                      支持部分精度与估算的日期
  src/fileformat.rs                格式判定与编码探测
  migrations/                      数据库结构，编译期嵌入二进制
crates/app                        桌面外壳 —— 窗口、IPC 命令、书库位置
  src/lib.rs                        命令接口与 DTO
  tauri.conf.json                   窗口、打包与安全配置
  capabilities/default.json         窗口被允许做什么

```

`cargo test` 默认只跑 `crates/core`（见 `default-members`），以免拖慢快速的测试集。要连 app crate 一起跑就加 `--workspace`。

## 验证了什么

161 个 Rust 测试，外加界面的类型检查（`npm run typecheck`）。前端本身没有单元测试；原因见文末的*剩余工作*。

其中一部分是针对解析器和导入流程的验收测试。它跑在三个真实的 AO3 下载文件上，而不是手写的假数据，因此检验的是"AO3 实际输出的东西"：

| 文件 | 作品 | 角色 |
|---|---|---|
| `One_two_three.html` | works/7929115，英文，67,851 词 | 原文 |
| `Er_San.html` | works/14885858，中文，94,736 词 | 上者的译文 |
| `Zong_Lu_Jian_Dan_Di_Sha.html` | works/91520771，中文，22,210 词 | 无关作品 |

这些下载文件**没有提交进仓库**——它们是别人的作品，放进公开仓库等于二次发布。测试是从仓库根目录读取的，所以要跑那 21 个测试就把它们复制到根目录；在开发这台机器上它们存放在 `D:\dsh\books\_original-downloads`。没有这些文件时，每个测试会跳过，测试集仍然全绿。跳过会打印出来，所以用 `cargo test -- --nocapture` 可以看到：

```
SKIP real_samples: sample file(s) not present: Er_San.html
test result: ok. 17 passed; 0 failed; 0 ignored
```

注意：跳过在结果里显示为 `passed` 而不是 `ignored`。Rust 没有运行时的"忽略"状态，所以这些守卫是通过 `Result` 签名提前返回来实现的。

支撑整个设计的行为：

- 同时导入原文和译文时，**不需要任何手动步骤就能配对上**
- 只导入其中一个时，另一个会被记为待定；等第二个文件到位——哪怕是在之后的某次会话里——配对会自动完成
- 重复导入同一个文件夹是**空操作**：内容哈希能识别出重复，且不会重写任何元数据，所以你手工做的修正不会丢
- 作品和它的译文是两条独立记录，由 `work_relations` 关联
- 原文自己声明的德语译文（不在书库里）会作为"建议"保留下来，而不是被丢掉

## 界面

一个作品列表加一个用于编辑的详情面板。所有数据都在内存里，所以在这个量级下筛选和排序是即时的。

- **计数**把作品数和文件数分开报告：`共 87 篇 · 84 篇有文件 · 3 篇仅记录 · 126 个文件`。有筛选时会追加 `筛选出 12 / 87 篇`，所以永远清楚哪个数字是哪个。
- **搜索**覆盖标题、作者、标签、AO3 标签、你的备注和摘要，并支持可选的字段前缀（`tag:慢热`、`title:杀人`、`author:lisabart`）。标点和大小写会被折叠，所以 `一二三` 能找到 `一，二，三`。
- **排序**可按发布日期、字数、录入顺序或标题，升序或降序。没有日期的作品无论正序倒序都排在最后，因为"未知"不等于"很久以前"。
- **分组**让作品与其译文保持相邻；用开关可以关掉它，得到一份严格扁平的列表——这正是"按字数排序"可信的前提。无论按什么排序，原文始终排在自己那一组的首位：只按排名锚定的话，按日期降序时更新的译文会排到它所翻译的作品前面。
- **行内的标签**可以点击：点一下筛选出带该标签的作品，再点一下取消筛选。工具栏里的标签列表是从作品推导出来的，而不是加载时拍下的快照，所以在编辑面板里新增的标签会立刻出现。
- **编辑**是一整块，而不是"标题 + 另开一个表单"：标题、作者、状态、发布与完成日期、标签、摘要和你的备注都是字段。日期接受 `2019`、`2019-06` 或 `2019-06-09`，并记录你实际给出的精度，另有一个 `约` 复选框用于标记猜测值。两个日期都是可选的——完成日期为空只表示未完结、弃坑或未知。
- **列宽**可以拖动表头边缘调整，工具栏里有四档**字号**。样式表里所有尺寸都用 `rem`，所以字号设置会一次性缩放整个界面，而不是只缩放一部分。
- **来源可辨**：估算字数显示为 `~23,159`，近似日期显示为 `~2019`，所以 AO3 明确给出的数字绝不会和猜测混淆。

## 配色

配色是蓝色系，源自 `#0000ff`。这个字面值刻意**没有**被用作文字颜色：在深色背景上它的对比度只有 **2.20:1**，连非文字 UI 所需的 3.0 门槛都不到——因为纯蓝是最暗的原色，人眼对它也最不敏感，看起来是"发闷"而不是"鲜明"。强调色采用的是同一色相、提高明度后的颜色：

| 用途 | 颜色 | 在 `--bg` 上的对比度 |
|---|---|---|
| 强调（链接、激活态） | `#6b7cff` | 5.37:1 |
| 突出（悬停） | `#8fa0ff` | 7.79:1 |
| 正文 | `#e8ecf8` | 16.0:1 |
| 弱化文字 | `#9aa6c4` | 7.78:1 |

`node scripts/pick-palette.mjs` 会打印完整的对比表，包括字面值 `#0000ff` 的参考数值。只有警告标签保持暖色（`#e8a05a`），这样在一片冷色界面里，出问题的地方会跳出来。

- **导入会先给出方案**——逐个文件标明：新建作品、并入已有作品、替换、还是作为重复跳过——并且在确认时**依据源路径重新生成**该方案，因此不可能把一个已经过时的方案套用到一个中途变化过的书库上。

## 文件存放位置

书库是占空间的大头——数据库加上所有导入的文件——所以它放在应用数据目录之外：

```
%APPDATA%\com.bookmarks.app\
  settings.json          ← 只有几百字节，别无其他
%USERPROFILE%\Documents\bookmarks\   ← 默认书库位置，可在设置中更改
  bookmarks.db
  library/
    000001/work.html
    000002/work.html
    000003/work.html
    000004/
      work.epub
      work.pdf
```

设置必须放在书库之外，因为"书库的位置"本身就是设置之一：它必须在书库被打开**之前**就能读到。把设置放在 `%APPDATA%` 还意味着 C 盘快满也不影响书库，而备份就是"复制书库文件夹"这么简单。

**更换位置**在设置里操作。整个移动过程是 复制 → 校验 → 切换 → 删除，所以中途失败时书库会留在原处，而不是变成移动了一半的状态；而如果目标位置已经有另一个书库，会直接拒绝而不是覆盖。

目录按作品 id 编号，文件名为 `work.<ext>`，因此同一作品的多种格式可以共存而不会出现 `(1)` 后缀，标题里含有 Windows 禁止的字符也不会破坏路径，重复导入某个格式会原地替换。原始文件名保存在数据库中用于显示。

### 同一文件的多个版本

连载作品会更新，完结作品也可能修订后重发，所以一个作品合法地可以持有同一格式的多份文件：

```
000001/
  work.html        ← 当前版本
  work.v2.html     ← 保留的较早修订
```

每个（作品, 格式）组合中恰好一个文件是 `current`，其余是 `archived`。具体怎么处理由导入决定，默认是**两者都保留**——重复导入通常意味着作品更新了，而丢掉一个修订版比多留一份副本更糟。默认行为可以在设置里翻过来，也可以在预览时针对单次导入覆盖。内容完全相同不会被当作新版本。已归档版本可以提升回当前版本，而当前版本不能直接删除，必须先提升另一个，所以作品不会落到"没有任何可读文件"的地步。

## 值得了解的设计取舍

**AO3 的下载文件里没有 `<meta name="ao3:*">` 标签。** 所有信息都从 DOM 读取。照着那些并不存在的标签去写的解析器会静默失败——什么都匹配不到，却不报任何错。

**一个作品等于一个语言版本，而不是一个故事。** 原文和它的译文是两行记录，由 `work_relations` 关联，因为译文有不同的作者、语言、字数和你的备注。*同一个*版本的多种格式（html/epub/txt/pdf）则是同一个作品下的多个文件。

**导入分两阶段。** `analyze` 提出方案，`execute` 才落地。分组是那种"错了用户会在意"的步骤，所以在写入任何东西之前，它可以被检视、被测试。

**分组依据证据，按强度排序。** 首先用 AO3 作品 id（它能在文件改名后依然有效）；其次是文件名主干与已存标题匹配。一个没有元数据、文件名又什么都不匹配的文件，会成为**独立**作品，而不是靠猜被并入——静默的错误合并会破坏一条已有记录，而多出一个条目只需要点一下就能合并。

**字数和日期都携带来源信息。** AO3 明确给出的数字被精确存储（67,851——不是估算）。用于 PDF/TXT 的计数器相对 AO3 自己的数字偏高：中文作品 +4.3%，英文作品 +1.6%，所以估算值会被标记并带 `~` 显示。日期以规范化的 ISO 字符串储存，附带精度（`day`/`month`/`year`）和 `is_approx` 标记，因此"来源只说了 2019"和"用户猜的 2019"始终可区分。

**搜索折叠标点，而不用索引。** 查询 `一二三` 必须能找到 `一，二，三`，而 SQLite 默认的分词器对中文做不到这一点（一串汉字会变成一个 token），trigram 分词器则在少于三个字符时无能为力。匹配采用在规范化文本上做子串搜索，在 `src/text.rs` 实现一次，并在 `src/library.ts::fold` 同步一份。大约超过一万个作品时应重新考虑这个方案。

**整个书库一次性读取。** 筛选、排序、分组和搜索都发生在界面里，所以这些规则集中在一个文件中，而不是拆散在 SQL 和 TypeScript 两边。在这个量级下，它也比一次往返更快。

**标签去重时不区分大小写**，而 AO3 自带的标签保存在另一个字段里，需要显式执行"加入我的标签"动作，以免你自己的筛选词汇被稀释。

**PDF 只贡献一条文件记录，不产生字数。** 文本提取需要专门的引擎，且对扫描件无效，所以不会凭空造一个数字出来。字数可以手工输入，此时会以 `word_count_source = 'manual'` 存储——这也正是它能在之后的导入中不被覆盖的原因。

**打开文件前会先检查它确实在书库内。** 路径来自数据库，但一行被篡改的记录不应该能够把任意路径交给系统去打开。

## 验证界面

`scripts/verify-ui.mjs` 通过 Chrome DevTools Protocol 驱动运行中的窗口，并对渲染结果做断言——共 22 项检查，覆盖标题对齐、槽位宽度、字号缩放、列宽拖拽、标签筛选、编辑表单和配色。它之所以存在，是因为"启动应用、看到进程还活着"完全不能证明窗口里显示的是什么；而好几个真实 bug（译文排到了自己那一组的前面、标题被一个徽章挤得不对齐、工具栏折成了两行）正是被这些断言抓到，而不是靠肉眼看出来的。

```
npm run dev:win                  # 启动开发服务器和窗口，已包含调试端口
node scripts/verify-ui.mjs 9223
```

`npm run dev:win` 会自己启用调试端口（见 `scripts/dev.mjs`），不需要手动设置任何东西。

它驱动的是**真实**窗口、针对**真实**书库，所以它为了验证筛选会更新而添加的那个标签是一次真实写入；脚本在结尾会把这个标签删掉，因此书库会被还原成运行前的样子。

`scripts/inspect-ui.mjs` 只是打印渲染出来的界面而不做断言，当"看起来不对"而你想知道 DOM 里究竟是什么时，它很有用。

## 这个环境里的网络访问

沙箱的精简令牌破坏了 Schannel，因此 cargo、curl、PowerShell 和 git 的 TLS 都会失败（`SEC_E_NO_CREDENTIALS`），而 Node 自己的 TLS 栈却能正常访问同样的主机。有两个脚本用于绕过；**在普通机器上两者都不需要**：

- `scripts/fetch-rustup.mjs` 用 Node 的 TLS 下载 Rust 工具链，因为 `rustup-init.exe` 自带的下载器在这里无法完成握手。
- `scripts/net-bridge.mjs` 是一个本地的 HTTP→HTTPS 桥，让 cargo 能够拉取 crate。通过 `.cargo/config.toml` 把 cargo 指向它，然后启动：

  ```
  node scripts/net-bridge.mjs 23456 &
  cargo build --workspace
  ```

  在 TLS 正常的机器上，删掉 `.cargo/config.toml`（或其中那两行 registry 配置），cargo 就会直接使用公共 HTTPS 源。`npm install` 借助系统代理即可正常工作。这个文件已被 git 忽略，因为它指向 `127.0.0.1`，在任何别的机器上都会让 `cargo build` 失败。

`scripts/make-icons.mjs` 生成应用图标，用一个内置的小型编码器写出 PNG 和 ICO，因此不需要任何图像工具。

## 剩余工作

1. **CSV 导入**，用于 AO3 书签小工具导出的数据。没有文件的作品已经可以手工录入（`status = 'record_only'`），并且在计数上与有文件的作品分开统计。
2. **手动的"关联到…"操作**，作为兜底：当译文文件里没有 AO3 id 时使用。自动配对只能看到 AO3 标记里写明的信息。
3. **EPUB 文本提取**，让 EPUB 也能贡献字数和可搜索文本。目前 EPUB 会被保存并列出，但字数必须手工输入。
4. **PDF 文本提取**是刻意不做的。促使考虑这件事的那个样本，57 KB 的故事却有 9.5 MB，说明它是扫描的页面图像而非文本；要做就得配 OCR 才有意义。
5. **前端单元测试。** 筛选、排序、分组和搜索的逻辑在 `src/library.ts`，目前只有类型检查、没有测试覆盖；其中最有价值的是把折叠规则与 Rust 侧的一致性固定下来。
6. **打包**：`npm run app:build` 生成安装包。代码签名被跳过——未签名的 `.exe` 首次运行会触发 SmartScreen 警告。
7. **退出时做 WAL checkpoint**，这样备份书库只需要 `bookmarks.db`，而不必连 `-wal` 和 `-shm` 一起复制。目前 `-wal` 文件里存着大部分最近的写入，这让"直接复制数据库"这件事在细微处是不安全的。
